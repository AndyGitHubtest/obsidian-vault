## P0 - 逻辑硬伤（不修复实盘会亏）

### P0-1: 延续评分使用了"未来数据"

**问题位置：** 信号架构.md §6.4 延续评分

**问题描述：**
延续评分中以下指标需要"爆发发生后"的数据，但在入场决策时这些数据还不存在：

```python
# 回撤深度 - 需要爆发后的回撤数据
pullback_ratio = calc_pullback_ratio(bars)  # 爆发还没完成，哪来的回撤？

# 突破位站稳比例 - 需要后续K线
stand_ratio = calc_stand_ratio(bars)  # 刚突破，怎么算站稳？

# 后续量能维持 - 需要后续数据
vol_maintain = calc_vol_maintain(bars)  # 这是事后指标
```

**实战后果：**
- 回测中这些指标都能算出来（因为历史数据完整）
- 实盘中这些指标在入场时**根本不存在**
- 导致回测评分虚高，实盘评分低，两者严重不一致

**修复方案：**
```python
# 方案 A：用"突破前"的数据替代
# - 回撤深度 → 用突破前的回踩深度
# - 站稳比例 → 用突破前在关键位的表现
# - 量能维持 → 用突破前的量能趋势

# 方案 B：延续评分只用于"持仓管理"，不用于"入场决策"
# - 入场只看压缩分 + 爆发分 + 执行分
# - 延续分用于持仓期间动态评估，决定加减仓

# 推荐方案 B
```

**严重度：** P0 - 回测和实盘会严重脱节

---

### P0-2: 综合评分阈值 65 分没有依据

**问题位置：** 信号架构.md §7.1

**问题描述：**
```python
if score < 65:
    return False, f'综合评分不足: {score}'
```
- 65 分是拍脑袋定的
- 评分系统刚设计，没有历史数据支撑
- 不同市场环境下的"好信号"分数可能完全不同

**实战后果：**
- 可能错过大量好信号（阈值太高）
- 也可能放过大量垃圾信号（阈值太低）
- 评分分布可能呈正态分布，65 分可能过滤掉 70% 的信号

**修复方案：**
```python
# 方案 A：先用低阈值放行，回测后根据分数分布确定
SCORE_THRESHOLD = None  # 初始不限制

# 回测后分析：
# - 统计每个分数段的胜率/盈亏比
# - 找到盈亏比开始下降的分数点作为阈值

# 方案 B：用相对排名代替绝对分数
# - 每次扫描取 Top N（如 Top 5）
# - 不关心绝对分数，只关心相对排序
```

**严重度：** P0 - 参数没有数据支撑，可能导致策略失效

### P0-3: 多周期联动的数据延迟问题

**问题位置：** 信号架构.md §5.5

**问题描述：**
```python
def check_multi_timeframe(symbol, tf_trigger='5m', tf_confirm='15m', tf_context='1h'):
    context_bars = get_bars(symbol, tf_context, 50)
    confirm_bars = get_bars(symbol, tf_confirm, 30)
```
- 5m 触发时，15m K 线可能还没收盘
- 1h K 线更是严重滞后
- 实盘中会出现"5m 看到突破了，但 15m 这根 K 线还有 3 分钟才收"

**实战后果：**
- 回测中所有 K 线都是完整的，多周期确认很容易
- 实盘中 5m 触发时，15m/1h 都是"进行中"的 K 线
- 要么错过信号（等 15m 收盘时价格已经涨远了）
- 要么用不完整 K 线做判断（信号质量差）

**修复方案：**
```python
# 方案 A：5m 触发时，15m 确认用"已完成的上一根 15m"
# 缺点：确认滞后 5-15 分钟

# 方案 B：5m 触发时，15m 确认用"当前进行中的 15m（部分数据）"
# 缺点：信号不稳定，可能 15m 最后 5 分钟反转

# 方案 C：只在 5m 周期做决策，多周期用于"环境过滤"而非"确认"
# - 1h 趋势方向只做加减分，不做硬性过滤
# - 这样不会引入延迟

# 推荐方案 C
```

**严重度：** P0 - 回测和实盘的周期对齐方式完全不同

## P1 - 实战风险（建议修复）

### P1-1: 压缩检测的滞后性

**问题：** 当你确认"压缩完成"时，突破可能已经发生了 2-3 根 K 线

```python
# 压缩需要连续 N 根 K 线满足条件
# 但突破往往就在压缩结束的下一两根
# 等你确认完压缩质量，价格可能已经涨了 2-3%
```

**实战后果：**
- 入场点位偏高
- 止损距离变大 → 仓位变小 → 盈亏比变差
- 好的信号可能因为"确认太慢"而错过

**建议：** 压缩检测可以做"预判式"，不等完全确认，只要压缩特征出现就加入候选池，突破确认时直接触发

---

### P1-2: 成交量数据可以做假

**问题：** 币安等交易所存在刷量行为，成交量数据不可完全信任

```python
vol_ratio = bar.volume / vol_ma  # 如果 volume 是刷出来的，这个指标就废了
```

**实战后果：**
- 假突破配合假量能 = 双重欺骗
- 成交量评分可能给出错误的高分

**建议：** 
- 用成交额（amount）替代或辅助成交量
- 用主动买入量替代总成交量（如果能拿到）
- 用 K 线实体大小替代部分量能判断

---

### P1-3: 4 阶段止盈等比例分配不合理

**问题：** 每批 25% 的等比例分配没有根据实际行情特点优化

```python
self.phases = [
    {'ratio': 0.25, 'trigger': 'fixed_rr_1.5'},
    {'ratio': 0.25, 'trigger': 'fixed_rr_2.5'},
    {'ratio': 0.25, 'trigger': 'resistance_level'},
    {'ratio': 0.25, 'trigger': 'trailing_stop'},
]
```

**实战问题：**
- 第一批 25% 太少，可能不够覆盖手续费和止损成本
- 如果行情只到 1:1.5 就反转，只走了 25% 仓位
- 爆发性行情往往快速到位，4 阶段可能只触发前 2 个

**建议：**
- 第一批加大到 35-40%，确保基本利润锁定
- 最后一批留给移动止盈的减少到 15-20%
- 根据历史回测的"最大常见涨幅"来设计止盈阶段

---

### P1-4: 时间止损 24 根（2 小时）太短

**问题：**
```python
if position.hold_bars > 24:  # 2小时
```

**实战问题：**
- 爆点策略的完整行情周期可能 3-6 小时
- 2 小时就止损可能错过主升段
- 但太长又会把资金锁在没行情的标的上

**建议：**
- 根据波动率动态调整：波动率高的品种给更多时间
- 根据盈利状态调整：如果已经盈利，给更多时间
- 设置硬上限但不设下限

---

### P1-5: 市场环境过滤需要实时数据

**问题：**
```python
up_ratio = sum(1 for s in symbols if s.change_24h > 0) / len(symbols)
btc_trend = get_btc_trend()
market_atr = np.median([s.atr_pct for s in symbols])
```

**实战问题：**
- 全市场扫描需要获取几百个币的数据
- 每次扫描可能需要 5-10 秒
- 5m 周期只有 300 秒，10 秒的延迟就是 3% 的时间浪费

**建议：**
- 市场环境指标可以低频更新（每 30 分钟一次）
- 不需要每根 5m K 线都重新计算
- BTC 趋势可以用本地缓存

## P2 - 优化建议

### P2-1: 垃圾币过滤规则不够量化

**问题：** "频繁插针"、"盘口薄"、"滑点高"这些描述需要量化为具体阈值

### P2-2: 压缩质量过滤中的"结构判断"函数未定义

```python
structure = classify_structure(bars[-period:])  # 这个函数没有实现
```
箱体/旗形/三角/平台的分类算法复杂，实盘中准确率不高，建议简化或去掉

### P2-3: 连续位移确认的阈值过于严格

```python
cum_ret_3 > 0.015 and   # 3根累计>1.5%
cum_ret_5 > 0.025 and   # 5根累计>2.5%
cum_ret_8 > 0.035       # 8根累计>3.5%
```
三个条件同时满足在 5m 周期非常苛刻，可能过滤掉大量有效信号。建议用"或"逻辑或降低阈值

### P2-4: 评分权重（25/30/30/15）没有数据支撑

压缩分 25% + 爆发分 30% + 延续分 30% + 执行分 15% 是主观分配的。建议：
- 先用等权重（各 25%）
- 回测后根据各分项与收益的相关性调整权重

## 总结

**策略设计质量：** 85/100（框架完整，逻辑清晰）

**最大风险：** 回测能跑通但实盘亏钱，因为：
1. 延续了评分使用了未来数据（回测有，实盘没有）
2. 多周期确认在实盘中存在数据延迟
3. 评分阈值没有历史数据支撑

**最大优势：** 
1. 5 层模块设计清晰，代码实现不会乱
2. 失效检测机制完善，不幻想不硬扛
3. 仓位管理考虑了环境和连亏，不是固定仓位
4. 日内交易不持仓过夜，风险可控

**一句话：** 设计得很好，但要把"回测逻辑"和"实盘逻辑"对齐。现在文档里有几个地方是用"上帝视角"写的，实盘中看不到那些数据。修复后策略可以进回测。
