# 🔄 状态机转换自动化标准

> 定义每个状态转换的精确条件、自动动作、回滚路径

---

```
┌─────────────────────────────────────────────────────┐
│                                                     │
│  INIT ──→ PLANNING ──→ DESIGN ──→ DEVELOP          │
│   │         │           │           │               │
│   │         │           │           ↓               │
│   │         │           │         TEST ←────────┐   │

│                                                     │

```

## 转换规则详情

### TRANSITION-001: INIT → PLANNING

| 项目 | 内容 |
|------|------|
| 前置状态 | INIT |
| 目标状态 | PLANNING |
| 触发条件 | 用户输入任务，AI 完成初始化 |
| 自动检查项 | Task.md 已创建、任务已拆解、项目类型已确认 |
| 自动动作 | 创建 PRD.md 骨架、填写项目背景 |
| 失败处理 | 用户需求不清 → 标注假设，继续推进 |
| 日志格式 | `[时间] 状态 INIT→PLANNING: 任务拆解完成，进入需求分析` |

### TRANSITION-002: PLANNING → DESIGN

| 项目 | 内容 |
|------|------|
| 前置状态 | PLANNING |
| 目标状态 | DESIGN |
| 触发条件 | PRD.md 完成填写 |
| 自动检查项 | PRD 完整、目标明确、范围清晰、风险已识别 |
| 自动动作 | 创建 ARCH.md 骨架、复制架构模板 |
| 失败处理 | PRD 不完整 → AI 自动补充缺失项 |
| 日志格式 | `[时间] 状态 PLANNING→DESIGN: PRD 完成，进入架构设计` |

### TRANSITION-003: DESIGN → DEVELOP

| 项目 | 内容 |
|------|------|
| 前置状态 | DESIGN |
| 目标状态 | DEVELOP |
| 触发条件 | ARCH.md 完成填写 |
| 自动检查项 | ARCH 覆盖 PRD、模块划分清晰、技术选型确定 |
| 自动动作 | 创建代码目录结构、初始化开发环境 |
| 失败处理 | ARCH 未覆盖 PRD → AI 自动补充 |
| 日志格式 | `[时间] 状态 DESIGN→DEVELOP: 架构完成，进入编码阶段` |

### TRANSITION-004: DEVELOP → TEST

| 项目 | 内容 |
|------|------|
| 前置状态 | DEVELOP |
| 目标状态 | TEST |
| 触发条件 | 所有 P0 任务完成，代码无编译错误 |
| 自动检查项 | 代码完整、无语法错误、文档已同步、Git 已提交 |
| 自动动作 | 创建 TEST.md、准备测试环境 |
| 失败处理 | 代码不完整 → 继续开发，不流转 |
| 日志格式 | `[时间] 状态 DEVELOP→TEST: 开发完成，进入测试阶段` |

### TRANSITION-005: TEST → DEPLOY

| 项目 | 内容 |
|------|------|
| 前置状态 | TEST |
| 目标状态 | DEPLOY |
| 触发条件 | 测试全部通过，指标达标 |
| 自动检查项 | 测试覆盖率达标、无未修复 Bug、回测指标合格（如适用） |
| 自动动作 | 准备部署环境、配置部署参数 |
| 失败处理 | 测试失败 → 回滚到 DEVELOP |
| 日志格式 | `[时间] 状态 TEST→DEPLOY: 测试通过，准备部署` |

### TRANSITION-006: DEPLOY → DONE

| 项目 | 内容 |
|------|------|
| 前置状态 | DEPLOY |
| 目标状态 | DONE |
| 触发条件 | 部署成功，验证通过 |
| 自动检查项 | 服务运行正常、监控已配置、文档完整、日志完整 |
| 自动动作 | 生成项目总结、标记完成 |
| 失败处理 | 部署失败 → 回滚到 TEST |
| 日志格式 | `[时间] 状态 DEPLOY→DONE: 部署完成，项目交付` |

## 回滚规则详情

### ROLLBACK-001: TEST → DEVELOP

| 项目 | 内容 |
|------|------|
| 触发条件 | 测试失败（单元/集成/回测不通过） |
| 自动动作 | 1. 记录失败原因到 TEST.md 2. 记录到 LOG.md 3. 状态回退到 DEVELOP 4. 标注失败任务 5. 开始修复 |
| 修复后 | 重新执行 TEST 阶段，不跳过 |
| 日志格式 | `[时间] 回滚 TEST→DEVELOP: 测试失败 - [原因]，开始修复` |

### ROLLBACK-002: DEPLOY → TEST

| 项目 | 内容 |
|------|------|
| 触发条件 | 部署失败、上线后异常 |
| 自动动作 | 1. 执行回滚操作 2. 记录失败原因 3. 状态回退到 TEST 4. 重新验证 |
| 修复后 | 重新执行 TEST → DEPLOY |
| 日志格式 | `[时间] 回滚 DEPLOY→TEST: 部署失败 - [原因]，回滚并重新验证` |

### ROLLBACK-003: 任意阶段 → 上阶段

| 项目 | 内容 |
|------|------|
| 触发条件 | 发现上游文档缺失或不一致 |
| 自动动作 | 1. 记录问题 2. 回到对应阶段补文档 3. 补完后重新流转 |
| 日志格式 | `[时间] 回滚 [当前]→[上阶段]: 发现 [问题]，补文档后重新流转` |

## 状态检查自动化

### 每次状态变更前自动执行
```
1. 读取 status.md → 确认当前状态
2. 读取 CHECKLIST.md → 获取当前→下一阶段检查项
3. 逐项检查 → 生成检查报告
4. 全部通过 → 执行状态流转
5. 有失败项 → 自动补全或回滚
6. 更新 status.md → 记录新状态
7. 更新 LOG.md → 记录状态变更
8. Git commit → 提交状态变更
```

### 检查失败处理
| 失败项 | 处理 |
|--------|------|
| 文档缺失 | 自动创建对应文档 |
| 文档不完整 | 自动补全缺失内容 |
| 代码错误 | 修复代码 |
| 测试不通过 | 回滚到 DEVELOP |
