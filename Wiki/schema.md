# Wiki Schema — LLM 维护规范

> 本文件定义 LLM Agent 如何读取、写入和维护 ~/Documents/Obsidian Vault/ 下的知识库。

## 角色定义

你是一个 **知识库维护者**，不仅仅是回答者。你的职责是：
1. **构建** — 将碎片信息编译成结构化 wiki 页面
2. **连接** — 维护双向链接 `[[ ]]`，确保知识网络连通
3. **更新** — 新信息出现时，主动更新相关页面，而不是只回答当前问题
4. **清理** — 定期发现矛盾、过时内容和孤立页面

## 目录约定

```
~/Documents/Obsidian Vault/
├── Wiki/                    # 核心知识库（LLM 拥有）
│   ├── index.md             # 内容目录，每次 ingest 后更新
│   ├── log.md               # 时间线日志，追加模式
│   ├── schema.md            # 本文件，操作规范
│   └── Sources/             # 原始来源备份
├── Hermes/                  # Hermes Agent 操作文档
├── 量化交易/                 # 策略与交易知识
├── 项目/                    # 其他项目文档
└── _Templates/              # 文档模板
```

## 文件格式

### 所有页面必须包含 frontmatter
```yaml
---
title: "页面标题"
created: 2026-04-06
updated: 2026-04-06
tags: [tag1, tag2]
---
```

### 链接规范
- 内部链接用 `[[页面名]]`
- 外部链接用 `[描述](URL)`
- 图片用 `![[filename.png]]`
- 跨目录引用用 `[[../路径/页面名]]`

## 操作流程

### Ingest（摄入新来源）
1. 读取来源内容
2. 提取关键信息（事实、参数、决策、引用）
3. 更新 `index.md` 中的索引
4. 创建或更新相关 wiki 页面
5. 维护双向链接
6. 追加记录到 `log.md`: `## [日期] ingest | 来源标题`

### Query（回答问题）
1. 先读 `index.md` 定位相关页面
2. 读取相关页面内容
3. 综合回答，引用具体页面: "如 [[页面名]] 所述..."
4. 如果发现新洞察，创建新页面并更新索引
5. 如果答案有价值（对比表/分析报告），也存为 wiki 页面

### Lint（健康检查）
1. 查找矛盾：不同页面对同一事实的描述不一致
2. 查找过时：标注 `%% 已废弃 %%` 旧内容
3. 查找孤儿：没有入链的页面（检查 index.md）
4. 查找缺口：频繁提及但无独立页面的概念
5. 追加记录到 `log.md`: `## [日期] lint | 修复 N 个问题`

## 内容原则

- **事实驱动** — 所有参数/公式/配置必须有来源
- **版本意识** — 策略代码和文档版本要对应
- **简洁优先** — 摘要+链接，不堆砌文字
- **中文为主** — 技术术语可保留英文原文

## 自动化触发

以下场景自动触发 wiki 更新：
- 代码改动涉及参数变更 → 更新 [[参数变更记录]]
- 策略逻辑修改 → 更新 [[策略规格说明]]
- 发现新的量化概念 → 添加到 [[知识框架]]
- Bug 修复 → 更新 [[Bug 总表]]

## 铁律体系（单一真相源）

> 所有铁律以本节为准。Memory 中仅存"铁律在 Wiki/schema.md"的引用。
> **冲突裁决规则**：L0 > L1 > L2，高级别覆盖低级别。

### L0 — 安全铁律（绝对不可违反，实盘相关）

| # | 铁律 | 违反后果 |
|---|------|----------|
| S1 | **所有回复必须基于实际代码（ssh grep 验证），不靠记忆猜测** | 决策基于错误信息 |
| S2 | **任何异常（网络/重启/延迟/部分成交）不能产生单边裸仓** | 重大资金风险 |
| S3 | **实盘改动必须备份+语法检查+重启+日志确认** | 策略崩溃无法恢复 |
| S4 | **任何网络异常后必须与交易所对账仓位** | 仓位状态不一致 |
| S5 | **数据库操作前必须备份** | 数据丢失 |

### L1 — 流程铁律（默认遵守，有例外时可跳过）

| # | 铁律 | 场景 |

| P1 | **未经确认绝不执行**（分析→方案→建议→等"执行"指令） | 执行类任务 |

| P4 | **换对必须 Walk-Forward 验证，稳健性 > 60%** | 策略验证 |
| P5 | **扫描数据必须 ≥ 180天（4320根1h），不足直接跳过** | 数据要求 |
| P6 | **策略逻辑修改必须跑最小回测验证** | 修改后验证 |
| P7 | **不预估任务时间** — 直接执行，完成后告知结果 | 所有任务 |
| P8 | **每次回复必须先确认用户问题**，再给出正式回答 | 每次对话 |

## P1 — 项目开发规则（通用版，从 0 到 1）

> 适用于量化策略、Web 应用、API 服务、爬虫/ETL 等所有项目。
> 每个阶段必须 P0 确认后才进入下一阶段。所有操作自动静默记录。

### 阶段一：需求定义（明确做什么、为什么做、成功标准）

| 步骤 | 动作 | 产出物 | 铁律关联 |
|------|------|--------|----------|
| 1.1 | 明确项目目标、用户群体、核心价值 | PRD 草稿 | P0 确认 |
| 1.2 | 确定技术栈、架构选型、第三方依赖 | 技术方案文档 | L1 依赖验证 |
| 1.3 | 定义验收标准、成功指标、失败边界 | 验收清单 | L0 安全底线 |
| 1.4 | 用户确认 PRD → 签字/确认 | PRD 定稿 | P0 确认 |

**检查清单（进入阶段二前）：**
- [ ] PRD 有明确的项目目标和成功标准
- [ ] 技术栈已选定，依赖项确认可用
- [ ] 用户已确认 PRD

**常见陷阱：**
- 目标模糊（"做一个好用的工具"）→ 必须量化（"3 秒内响应，日活 100+"）
- 忽略第三方依赖限制（API 限额、费率、可用性）
- 验收标准不可测量

### 阶段二：基础设施（骨架搭建、环境配置、数据/依赖就位）

| 步骤 | 动作 | 产出物 | 铁律关联 |
|------|------|--------|----------|
| 2.1 | 项目初始化（目录结构、git、依赖管理） | 可运行的空项目 | L1 git 初始化 |
| 2.2 | 开发环境搭建（本地/远程、数据库、中间件） | 环境配置文档 | L0 备份配置 |
| 2.3 | CI/CD 管道配置（自动构建、测试、部署） | CI/CD 配置文件 | L1 自动化 |
| 2.4 | 数据源/第三方服务对接 + 连通性验证 | 连通性测试报告 | P0 确认 |

**检查清单（进入阶段三前）：**
- [ ] `git init` 完成，远程仓库已创建
- [ ] 项目骨架可运行（Hello World / 空路由 / 空策略）
- [ ] 数据库/数据源连通性验证通过
- [ ] CI/CD 管道能自动构建

**常见陷阱：**
- 目录结构混乱，后期难以维护 → 参考 `_Templates/` 中的标准结构
- 忽略环境差异（本地 vs 服务器 vs 生产）
- 数据源未验证就开始开发（API 变了、Key 过期了）

### 阶段三：核心开发（MVP 实现、迭代开发、测试覆盖）

| 步骤 | 动作 | 产出物 | 铁律关联 |
|------|------|--------|----------|
| 3.1 | 最小可用版本（MVP）— 核心功能跑通 | MVP 代码 | L2 小步快跑 |
| 3.2 | 每步 git commit + push（小粒度提交） | Git 历史 | L1 自动提交 |
| 3.3 | 单元测试 + 集成测试（核心逻辑覆盖） | 测试报告 | P0 确认 |
| 3.4 | 代码审查 + 修复问题（安全/性能/逻辑） | 审查记录 | L0 代码验证 |

**检查清单（进入阶段四前）：**
- [ ] MVP 核心功能可运行
- [ ] 核心逻辑有单元测试覆盖（>70%）
- [ ] 无安全漏洞（SQL 注入、XSS、敏感信息泄露）
- [ ] 用户已审查 MVP 功能

**常见陷阱：**
- 大爆炸式提交（一次性提交几百行）→ 每个功能点独立提交
- 忽略错误处理（网络超时、数据缺失、API 限流）
- 测试只覆盖 happy path，不覆盖异常路径

### 阶段四：测试验证（功能、性能、安全、用户验收）

| 步骤 | 动作 | 产出物 | 铁律关联 |
|------|------|--------|----------|
| 4.1 | 功能测试（逐条验证验收清单） | 功能测试报告 | L1 真实数据 |
| 4.2 | 性能/安全测试（压测、扫描、边界值） | 性能/安全报告 | L0 安全底线 |
| 4.3 | 用户验收测试（UAT） | 验收通过/修改清单 | P0 确认 |

**检查清单（进入阶段五前）：**
- [ ] 所有验收标准已满足
- [ ] 性能指标达标（响应时间、吞吐量、并发）
- [ ] 安全扫描无高危漏洞
- [ ] 用户已签字验收

**常见陷阱：**
- 用 mock 数据测试，上线后真实数据格式不一致
- 忽略边界条件（空数据、超大输入、并发冲突）
- 性能测试环境与实际生产环境差异过大

### 阶段五：部署上线（生产环境、灰度发布、监控接入）

| 步骤 | 动作 | 产出物 | 铁律关联 |
|------|------|--------|----------|
| 5.1 | 生产环境准备（服务器、域名、SSL、数据库） | 环境配置清单 | L0 备份 |
| 5.2 | 部署 + 冒烟测试（核心功能验证） | 部署报告 | L0 语法检查 + 重启 + 日志 |
| 5.3 | 监控/日志/告警配置 | 可观测性配置 | P0 确认 |

**检查清单（进入阶段六前）：**
- [ ] 生产环境与测试环境配置一致
- [ ] 冒烟测试通过（登录、核心流程、数据流）
- [ ] 监控仪表盘已接入（CPU/内存/错误率/延迟）
- [ ] 告警规则已配置（阈值、通知渠道）

**常见陷阱：**
- 配置文件硬编码密钥/密码 → 使用环境变量或密钥管理
- 忽略日志轮转（日志撑爆磁盘）
- 监控告警未测试（出问题时收不到通知）

### 阶段六：运维迭代（监控、Bug 修复、功能迭代）

| 步骤 | 动作 | 产出物 | 铁律关联 |
|------|------|--------|----------|
| 6.1 | 日常监控 + 健康检查 | 监控报告 | 静默记录 |
| 6.2 | Bug 修复（复现→修复→验证→部署） | Bug 修复记录 | L0 备份 + 验证 |
| 6.3 | 功能迭代（回到阶段一） | 迭代计划 | P0 确认 |

**检查清单（持续）：**
- [ ] 每日检查服务状态和关键指标
- [ ] Bug 修复后更新 Bug 总表
- [ ] 每次迭代保留完整 Git 历史

**常见陷阱：**
- 线上问题不记录，重复踩坑 → 必须写入 Bug 库
- 监控数据不分析，告警疲劳 → 定期回顾告警规则
- 迭代没有明确目标，盲目加功能 → 每次迭代必须有 PRD

### 贯穿规则（所有阶段必须遵守）

| 规则 | 说明 |
|------|------|
| 每个阶段必须 P0 确认后才进入下一阶段 | 铁律 P0 |
| 所有代码改动自动 git commit + push | 铁律 L1 |
| 每次操作自动记录到 log.md | 静默工作记忆 |
| 不预估任务时间 | 铁律 L1 |
| 所有分析基于实际代码（ssh grep） | 铁律 L0 |
| 代码修改优于新增，精简优于冗余 | 铁律 L2 |

| 项目类型 | 阶段二重点 | 阶段四重点 | 特殊要求 |

## P1 补充 — 多 Agent 协作与记忆传递规则

> 适用于需要并行处理、独立会话、长时间运行的复杂任务。

### 什么时候用多 Agent

| 场景 | `delegate_task` | 独立 Agent (`hermes-agent`) |
|------|-----------------|---------------------------|
| 2-3 个独立任务可并行 | ✅ | ❌ |
| 需要用户交互/确认 | ❌ | ❌ |
| 长时间后台任务 | ❌ | ✅ |
| 复杂问题多角度分析 | ✅ | ✅ |
| 需要独立终端会话 | ✅ | ✅ |
| 子任务有强依赖关系 | ❌ | ❌ |

### 记忆传递规则（关键）

**子代理没有主 Agent 的 Memory 和对话历史**，必须通过 `context` 字段显式传递：

```
context 必须包含：
1. 相关文件路径（代码/配置/日志/数据库）
2. 错误信息（完整错误栈，不省略）
3. 约束条件（相关铁律/用户偏好/环境信息）
4. 期望输出格式（JSON/Markdown/具体字段）
```

### 记忆回收规则

子代理完成后：

| 步骤 | 动作 | 铁律关联 |
|------|------|----------|
| 1 | 主 Agent 审查子代理结果 | P0 确认 |
| 2 | 关键发现 → 写入 log.md | 静默记录 |
| 3 | 环境/参数变化 → 更新 Memory | 记忆更新 |
| 4 | 代码改动 → git commit + push | L1 自动提交 |

### 铁律约束传递

所有子代理**自动继承**以下约束（通过 context 传递）：

| 铁律 | 传递方式 |
|------|----------|
| L0: 不产生裸仓 / 基于代码验证 | context 中注明 |
| L1: git commit + push | 主 Agent 统一执行 |
| L1: 不预估时间 | context 中注明 |
| L2: 中文沟通 | context 中注明 |

### 典型使用模式

```python
# 模式 1：并行独立任务
delegate_task(tasks=[
    {"goal": "任务 A 目标", "context": "文件路径 + 约束"},
    {"goal": "任务 B 目标", "context": "文件路径 + 约束"},
    {"goal": "任务 C 目标", "context": "文件路径 + 约束"}
])

# 模式 2：复杂问题多视角分析
delegate_task(goal="分析问题 X", context="完整背景 + 约束", toolsets=["terminal", "file", "web"])
```

### 限制与注意事项

- 子代理**不能**使用 `clarify`（无法问用户问题）
- 子代理**不能**调用 `delegate_task`（禁止递归）
- 每个子代理最多 50 次工具调用
- 复杂任务建议拆分后并行，而非单任务串行

## 自动触发

**用户不需要做任何额外操作。** 每次任务完成后自动执行：

1. **追加到 log.md**：`## [日期 时间] task | 任务简述`
   - 改了哪个文件/参数
   - 为什么改（原因）
   - 结果如何
   - git commit hash（如果有）

2. **更新 Memory**：关键事实变化时自动替换旧条目
   - 参数变更
   - 服务器状态变化
   - 用户偏好调整
   - 环境信息更新

3. **定期分析**（每周/用户询问时）：
   - 工作模式总结
   - 反复出现的问题
   - 进展与阻塞

4. **响应查询**：
   - "这周干了什么" → 从 log.md 提取
   - "上次参数多少" → 从记录查找
   - "工作进展" → 综合分析
